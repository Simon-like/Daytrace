# 项目结构与文档治理

日期：2026-10-30。状态：仓库组织基线；技术方向更新为Next.js + NestJS + pnpm monorepo，部署前提待验证。

## 一张目录地图

```text
apps/site/             Next.js目标应用；目前无框架脚手架
apps/api/              NestJS目标应用，待ENGINE创建
packages/              contracts/config目标共享包，待ENGINE创建
  src/features/        records / reader / search / owner
  src/server/          仅Next服务端API适配；业务/权限在Nest
content/               站点的个人记录，public / private / fixtures
knowledge/             研发知识：inbox / learnings / playbooks
docs/                  产品、设计、架构、研究、项目报告、历史
design/                已有主题、原型、照片、来源和资产索引
coordination/          中央任务队列、任务卡、交接与评审
experiments/           按任务ID隔离的技术PoC
tests/                 foundation / unit / integration / e2e / fixtures
scripts/               仓库校验与任务管理
templates/content/     技术/生活/随想的整理模板
ops/                   部署、备份、恢复等运行文档边界
```

采用单仓库site/api两个应用，contracts/config服务两个真实消费者；这是用户确认全栈方向后的增量调整。仍不引入微服务、微前端、独立UI包或复杂构建编排。正式目录由ENGINE按任务创建，不把目标树当成已存在。

## 三种“知识”不要混在一起

| 信息 | 权威位置 | 例子 |
| --- | --- | --- |
| 产品怎么建 | docs | PRD、排期、技术决定、验收报告 |
| 研发学到了什么 | knowledge | 目录锚点偏移、模态焦点、响应图解的可复用方法 |
| 主人想保存什么 | content | 微前端实践、真实菜谱、个人感悟 |

design是原始视觉与运行原型的资产来源，不是另一套正式应用。它们的相对引用保留，避免把历史原型挪动后损坏。

## 单一事实来源

| 问题 | 看哪里 |
| --- | --- |
| 当前需求/优先级 | docs/product/PRD-v1.0.md |
| 视觉和手写原则 | design/视觉风格基线-v1.0.md |
| 已通过什么检查 | 对应阶段报告与证据 |
| 当前阶段/下一步 | docs/project/项目进度.md |
| 任务归谁/是否完成 | coordination/board.json |
| 技术为什么这样选 | docs/architecture/decisions/ |
| 接手先了解什么 | docs/项目记忆.md的摘要与链接 |
| 哪些素材能用 | design/资产索引.md与原交付说明 |

记忆库只写摘要和定位，不能代替源文档。报告保留历史，最新进度有明确更新时间；不要把旧报告中的“未开始”错误读成当前状态。

## 文档分类与生命周期

- product：产品范围与验收。
- design：模块行为、响应式、字体和动效说明；原图在根design。
- architecture：技术研究、模块契约与ADR。
- research：参考资料和工具调研，不视为已作决定。
- project：看板、路线图、阶段报告、决定记录。
- context：稳定共识的定位、当前工作和任务接力；不另维护一份PRD。
- archive：已经被正式文档替代的草案；旧入口保留转向说明。

catalog.json登记权威文档的路径、职责、状态与维护角色，由校验脚本生成目录块。未进入catalog的独立实验/交接允许存在，但不能自称取代正式基线。

技术ADR采用proposed/accepted/superseded；写清依据、备选、代价、验证和重审触发。用户确认、执行者实施决定、纯建议三者不能混写。

## 维护节奏

每任务结束：交接单和证据。每次集成：台账、相关知识条目、目录/记忆摘要。每阶段结束：阶段报告和下一门槛。实际发生才更新，不为了日期好看自动标完成。

用户改变当前范围时先更新context/当前工作上下文，再更新项目记忆与必要的台账说明。任务登记不等于执行授权，尤其不能把未共同讨论的技术候选当作下一Agent应自动执行的指令。

文档变更默认先修权威来源，再更新引用/摘要。范围变化更新PRD与变更记录；参数微调更新设计说明；技术变更更新ADR。避免同一个规则复制到五份文件后各自演进。

## Git与内容隔离

普通提交保存源码、项目文档、工程知识、明确公开内容与选定资产。node_modules、构建产物、凭据与content/private均忽略；私密记录必须另外备份，Git忽略不等于数据已保护或已备份。

已存在GitHub远端，实际同步状态以Git为准。worktree基于实际提交，跨设备分工由中央协调者维护队列；文件锁不能协调不同主机上的台账副本。
