# 阅读型产品动效调研：从优秀团队方法到 Daytrace 准则

调研日期：2026-11-02。任务：MOTION-001。范围：为技术观察、厨房实践、生活记录与个人感想并存的阅读型站点制定动效方法，不评估营销页、3D 展示或滚动叙事。

## 1. 结论先行

Daytrace 不复制某个团队的“招牌动画”，而吸收四类可验证的方法：

1. **Vercel：动效是有职责的工程。** 组件化、输入方式与辅助技术同等重要；实现成本必须与体验收益一起评估。
2. **Chrome/web.dev：流畅来自渲染路径与实测。** 优先 `transform`、`opacity`，避免布局和绘制抖动，以 Performance trace 而非肉眼感觉验收。
3. **Motion：弹簧用于直接操控，而非全站装饰。** 需要继承手势速度、可中断的物理运动时才有价值；简单界面过渡不必为此引入整套运行时。
4. **Stripe：复杂效果必须服务明确隐喻，并有成本边界。** 其一互动地球案例不证明阅读站需要 WebGL；对 Daytrace 的价值是“目标驱动、按成本取舍”。

因此，Daytrace 的路线是 **CSS transitions 优先、原生行为优先、小位移与短反馈、正文不做入场门槛、减少动态效果有等价体验、每个参考实现提交性能证据**。本调研不排出“全球最强团队”名次，也不把第三方文章里的时长和曲线冒充官方规范。

## 2. 证据口径

- **官方事实**：以下来源页面明确说明的能力、方法或案例。
- **项目建议**：由 Daytrace 的阅读目标推导出的参数、组件行为和技术优先级，需要后续实现验证。
- **项目实测**：本轮没有运行应用动画、没有 Performance trace、没有真机数据；不得把资料调研写成性能已经达标。

## 3. 团队与平台方法

| 来源 | 已核实的方法 | Daytrace 采用什么 | 不能据此推断什么 |
| --- | --- | --- | --- |
| [Vercel：Design Engineering at Vercel](https://vercel.com/blog/design-engineering-at-vercel) | 设计工程关注可复用 primitives、页面速度、跨浏览器、触摸／指针输入、用户偏好与辅助技术；追求精修交互和不丢帧，并评估实现成本与体验影响 | 动效放进本地组件契约；每个效果先说明职责，再测键盘、触摸、偏好和性能；非主焦点的动画可以不做 | 不能推断 Vercel 所有页面都使用某一时长、曲线或动画库 |
| [Chrome：High-performance animations](https://web.dev/articles/animations-guide) | 优先动画 `transform` 和 `opacity`，避免触发布局、绘制；`will-change` 应在确有性能问题时谨慎使用，并检查实际渲染 | 默认只动画合成友好属性；小面积颜色短过渡可接受；不预置全站 `will-change` | 不能声称只使用这两个属性就自动保证 60fps |
| [Chrome：prefers-reduced-motion](https://web.dev/articles/prefers-reduced-motion) | 对应操作系统减少动态效果偏好；CSS 与 JS 都应支持，JS 动画还需响应偏好变化；移除非必要运动 | 位移、缩放、弹簧和平滑滚动有静态回退；状态不能仅靠运动表达；运行中切换偏好也生效 | 减少动态效果不等于隐藏状态、禁用功能或降低文字对比 |
| [Chrome：Performance 面板](https://developer.chrome.com/docs/devtools/performance) | 可记录 FPS、主线程、forced reflow 等，并用 CPU throttling 检查较弱设备；教程使用 4× 节流示例 | 后续每个参考动效提交正常与 4× CPU 的 trace，检查长任务、强制布局、绘制和掉帧 | Chromium 桌面节流不是低端安卓或 iPhone Safari 的替代品 |
| [Motion：Transitions](https://motion.dev/docs/react-transitions) | 支持 tween、spring、inertia 与按属性配置；物理弹簧可继承手势或进行中动画的速度；duration-based spring 可生成 CSS | 简单组件用 CSS；确有可中断手势弹簧时再评估按需加载 Motion，不提前全站引入 | 不能据此宣称 Motion 是每个组件的必要依赖或天然零成本 |
| [Stripe：Building the Stripe Globe](https://stripe.com/blog/globe) | 复杂 WebGL 服务明确的视觉隐喻与交互目标，同时需要在生动体验和浏览器性能之间取舍 | 学习“视觉目标—实现成本—性能边界”的决策方法 | 不采用 WebGL、3D 地球、持续渲染循环作为阅读站方向 |

## 4. 对“高性能且丝滑”的拆解

### 4.1 响应先于运动

按钮、输入、选择、复制等操作应立即出现状态反馈。动画不能延迟事件处理、焦点移动、结果可读或辅助技术通知。加载状态先表达事实，再决定是否需要一个短过渡。

### 4.2 连续性比幅度重要

用户应知道菜单从哪里来、灯箱与哪张图片有关、关闭后焦点回到哪里。小范围位移和透明度足以表达关系；大幅飞行、回弹和全页转场会抢夺阅读注意力。

### 4.3 可打断是默认行为

动画进行中再次点击、按 Escape、切换路由或改变偏好时，控件必须从当前视觉状态平滑转向新状态，不能排队播放完整动画，也不能把用户锁在遮罩里。CSS transition 和普通控件状态机优先于不可中断的连续 keyframes。

### 4.4 阅读优先于展示

- 正文首屏和路由后的标题、段落默认可立即阅读，不等待入场。
- 保留浏览器自然滚动；不接管滚轮，不用滚动进度驱动正文。
- 长列表不逐项 stagger，搜索更新不逐条飞入。
- 不用持续噪点、视差、漂浮装饰、大面积 blur／filter 动画营造“高级感”。
- 弹簧只服务拖拽、抽屉等直接操控；按钮、正文、搜索结果不使用弹簧。

### 4.5 性能是证据，不是形容词

“只用了 transform”仍需检查是否同时修改布局、是否有过大合成层、是否有 React 每帧更新。验收至少包含动画中重复操作、CPU 节流、主线程长任务、forced reflow、布局稳定性和减少动态效果。平均 FPS 不能掩盖一次关键交互卡顿。

## 5. 技术路线比较

| 方案 | 适合 Daytrace 的场景 | 优点 | 成本与边界 | 决策 |
| --- | --- | --- | --- | --- |
| CSS transitions／keyframes + Radix `data-state` | 颜色反馈、Select、Checkbox、展开内容、抽屉、灯箱、Toast | 无新增运行时；易与 Tailwind 令牌和减少动态效果整合；transition 易中断 | 复杂物理手势和跨布局连续性能力有限 | **默认方案** |
| Web Animations API | 需要 JS 精确播放、取消、反向或监听完成，但仍由浏览器处理动画 | 原生、可控、无需 UI 动画框架 | 状态与生命周期需自行维护；不能用它绕过布局成本 | **按需局部采用** |
| Motion | 直接拖拽、抽屉速度继承、可中断弹簧等少数复杂交互 | 手势与物理运动能力完整，可按属性配置 | 增加依赖、包体和维护成本；不是简单过渡的必要条件 | **后续专项评估，不在本轮安装** |
| WebGL／持续渲染 | 明确需要 3D 或复杂粒子隐喻 | 表现力强 | 与阅读目标不匹配，耗电、包体、兼容性和无障碍成本高 | **不采用** |
| 滚动劫持／全站滚动动画库 | 营销叙事或特定展示页 | 可编排强视觉效果 | 破坏自然滚动、阅读和触摸预期，测试面大 | **不采用** |

## 6. 未采用为证据的资料

- Apple HIG、Material 动效页面本轮抓取只得到标题，未取得足以核验的具体条款，因此不引用其 token、时长或曲线。
- Linear 官方相关页面与检索结果未形成可靠的一手证据，不引用第三方转述的内部实现、时长或“Linear 感”参数。
- Awwwards、Godly 等作品库可启发视觉，但奖项、截图和展示视频不能证明中文长文阅读、低性能设备或辅助技术体验。

这些限制不妨碍本次形成项目准则；它们只意味着不得把未核实内容包装成权威事实。

## 7. 转化为 Daytrace 的实施顺序

1. **令牌与参考实现**：先在 Select、移动导航、图片灯箱三个代表组件验证“弹出层、空间连续性、图片层级”三类行为。
2. **微反馈迁移**：Button、Input、Checkbox、链接统一使用时长和曲线令牌，清理随意的 150／180／200ms 与不同 easing。
3. **状态与列表**：标签展开、搜索更新、Toast／错误只做克制的透明度反馈，不做高度和长列表动画。
4. **正文与路由**：保持立即阅读；目录定位只在显式点击时使用浏览器平滑滚动，减少动态效果时立即定位。
5. **性能与真机**：先交 Chromium 性能 trace，再做 WebKit／真实 iPhone；模拟视口不能替代后者。

具体项目参数、组件矩阵和验收清单见[动效系统基线 v1.0](../design/动效系统基线-v1.0.md)。
