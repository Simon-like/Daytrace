这是一份演示复盘。它用一个主子应用配置场景，保留“下一次该从哪里开始”的线索，而不只是框架名词。

## 先画清楚，谁负责什么

主应用负责入口、应用注册与导航；子应用负责自己的页面与资源。遇到白屏时，我先把问题分成三个层次：**有没有进入激活规则，有没有拿到资源，有没有完成挂载。**

| 观察位置 | 要确认的事 | 下一步 |
| --- | --- | --- |
| 地址与激活规则 | 路由是否命中子应用 | 查看注册配置与路径前缀 |
| Network 面板 | 入口 HTML、脚本和样式是否成功 | 对照资源路径与部署位置 |
| 生命周期日志 | mount 是否执行，是否报错 | 缩小到业务初始化或容器 |

## 把注册配置当作地图

```ts
registerMicroApps([
  {
    name: 'operations',
    entry: '/sub-apps/operations/',
    container: '#subapp-container',
    activeRule: '/operations',
  },
]);
```

这段代码只是示意，具体API以实际使用的框架为准。关键是把**浏览器地址、子应用入口和资源公共路径**放在一起看，而不是盲目修改每一个配置。

### 一个白屏问题的排查顺序

1. 直接打开子应用入口，确认它能独立加载。
2. 回到主应用，检查入口资源请求和返回类型。
3. 观察容器是否存在，生命周期是否运行。
4. 最后才检查子应用内部路由与业务初始化。

## 这次真正需要记住的

> 先回答“是哪一层没有发生”，再问“为什么没有发生”。

不需要背下全部源码。给自己留下注册入口、路由配置、资源请求和挂载日志的位置，下次就有一条可重走的路。
