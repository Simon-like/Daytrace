# Markdown 渲染、快捷导入与文章路由方案

日期：2026-11-03。任务：CONTENT-002。性质：源码核对后的推荐方案；本轮只更新文档，新增能力尚未实现。保留 Next + Nest、现有内容协议 v1、稳定 ID 路由与双端阅读设计。

## 1. 结论

推荐 **普通 Markdown + YAML 元数据 + Nest 服务端 unified/remark/rehype 管线 + Shiki 服务端高亮 + 按需 KaTeX/图表**。桌面和 H5 使用同一份经过权限检查的 HTML、目录和索引。上传不是提交 Git：主人在内容管理页选择或拖入 `.md`、附件或 ZIP，先生成私密草稿，检查预览后才显式发布。

采用这个组合的理由是扩展语法、定位源文件错误和内容迁移能力；不是声称它性能最快。现有 Marked + sanitize-html 保持可用，先通过兼容性样本与性能验证再替换。MDX、Fumadocs、Content Collections 不作为个人上传内容的权威读取链路。

本方案区分两步：现在确定渲染与内容管理方向；F1 真实身份完成前，F2 只能做合成数据或本机受控验证，不能把演示主人入口当生产上传权限。

## 3. 候选比较与适配判断

评价优先级：既有 Nest 权限和运行时上传兼容性 > 普通 Markdown 可迁移性 > 扩展语法和错误定位 > 双端一致与脚本负担 > 迁移成本。以下是工程判断，不是下载量排名或实测跑分。

| 候选 | 适用优势 | Daytrace 代价 | 选择 |
| --- | --- | --- | --- |
| Marked + sanitize-html（现有） | 已跑通、迁移成本最低，可扩展 token/renderer | 脚注、公式、源位置与更多自定义规则需要另接扩展并统一维护 | 过渡基线；若 unified 验证不达标继续使用 |
| unified + remark + rehype | AST 插件链便于目录、链接、附件、脚注、位置诊断复用；可服务端运行 | 插件顺序、ESM 与异步生命周期、sanitize 白名单要验证 | 推荐长期核心 |
| markdown-it | CommonMark、token 插件成熟、默认不启用 HTML | 同样需迁移；现有需求更看重 AST 统一转换与位置诊断 | 合理备选，无需同时引入 |
| react-markdown | React 元素映射方便，基于 unified，支持插件和服务端异步组件 | 若双端各自解析会形成第二套渲染规则；现有 API 是 HTML 产物 | 可用于独立 React 项目；这里不新增解析权威 |
| MDX / next-mdx-remote | Markdown 内嵌组件、适合可信仓库页面 | MDX 编译为 JS；上传内容不应获得执行能力；提高写作与迁移门槛 | 不用于上传正文 |
| Fumadocs | 文档网站、目录、搜索、页面结构完整 | 个人记录含私密、菜谱、随想及现有自定义双端设计，整套 UI 与内容源会重复建设；权限仍须自管 | 未来独立帮助中心可评估 |
| Content Collections | 文件集合生成类型安全数据，适合代码仓库随构建更新 | 生成导入产物与运行时上传/私密读取边界需要额外适配 | 不作为运行时内容库 |

依据：[unified](https://github.com/unifiedjs/unified)、[remark](https://github.com/remarkjs/remark)、[Marked](https://marked.js.org/using_advanced)、[markdown-it 安全说明](https://github.com/markdown-it/markdown-it/blob/master/docs/safety.md)、[react-markdown](https://github.com/remarkjs/react-markdown)、[MDX](https://mdxjs.com/docs/getting-started/)、[Fumadocs 内容集合](https://www.fumadocs.dev/docs/mdx/collections)、[Fumadocs 权限说明](https://www.fumadocs.dev/docs/guides/access-control)、[Content Collections](https://www.content-collections.dev/docs)。

## 4. 推荐渲染设计

处理顺序建议：

1. 读取和校验 YAML，普通正文解析为 mdast；记录原文位置与 frontmatter 行数偏移。
2. `remark-parse` + `remark-gfm`，需要公式才启用 `remark-math`；按白名单支持提示块。首期不引入可执行指令或任意组件。
3. 自有 AST 转换负责标题、目录、纯文本索引、相对文章链接和附件重写；从同一棵树生成，避免目录另做正则。正文 HTML、脚本、iframe 仍拒绝。原始导入的首个 H1 可经用户可见的转换提取为 title；标准内容包仍遵守 v1 正文无 H1。
4. `remark-rehype` 转 hast；URL/资源策略检查后用 `rehype-sanitize` 清理，只保留受支持标记与属性。
5. 仅可信插件执行 Shiki 和 KaTeX，生成站点控制的工具栏/图片包装；最后 `rehype-stringify`。sanitize 后的步骤也属于可信计算边界，禁止用户控制任意 HTML/样式或插件配置。按官方示例为数学标记、代码类设置白名单，不能为方便放开全局 `style`、SVG 或事件属性。
6. 输出 HTML、toc、plainText、依赖清单与 parseRevision；索引和缓存绑定同一内容快照及渲染配置版本。

[rehype-sanitize 官方示例](https://github.com/rehypejs/rehype-sanitize)解释了公式、高亮与清理顺序的兼容问题。`dangerouslySetInnerHTML` 只消费经过这个服务端边界的结果，客户端不得插入原始上传文本。

| 能力 | 建议级别 | 规则 |
| --- | --- | --- |
| 标题/段落/引用/列表/链接/图片/表格/任务列表/删除线 | 首期必备 | 保留现有中文排版、横滑、复制、灯箱与图片尺寸 |
| 脚注 | 首期必备 | remark-gfm；中文回链文案，脚注与目录共用 ID 规则 |
| 代码高亮 | 首期必备 | Shiki 服务端按语言白名单加载，未知语言退回纯文本；复制原始代码 |
| 数学公式 | 首期可选模块 | KaTeX 服务端，`trust: false`，限制展开和尺寸；错误转普通文本并定位 |
| 提示块 | 首期有限支持 | 仅 note/tip/warning 等允许类型；导出退回普通引用块也可读 |
| Mermaid | 后续独立切片 | 默认保留可复制源码；受控隔离渲染，禁远程资源与交互，限制图规模和超时；生成 SVG 不直接套用附件白名单 |
| Obsidian wikilink、嵌入、Typora 特性 | 导入适配按需增加 | 可解析的转普通链接；歧义提示选择，不能默默丢失；不是承诺兼容全部方言 |

[remark-gfm](https://github.com/remarkjs/remark-gfm)覆盖脚注、表格等；[Shiki rehype](https://shiki.style/packages/rehype)与[精简 bundle](https://shiki.style/guide/bundles)支持服务器按需高亮；[KaTeX 安全](https://katex.org/docs/security.html)要求注意 trust 和资源限制；[Mermaid 配置](https://mermaid.js.org/config/schema-docs/config.html)提供安全与规模相关选项，不能单靠 strict 就视为隔离完成。

迁移前还必须验证当前 Nest 编译配置与 ESM 插件的加载方式、异步解析如何进入快照构建；本轮未安装新依赖，未证实当前锁文件的具体兼容版本，不引用“最新版”作为工程保证。

## 5. 你以后怎样快速上传与管理

入口建议：桌面主人空间“内容”页，有“上传文档”“批量导入”；手机使用系统文件选择器，目录拖拽作为桌面增强。接受单个或多个 `.md`、Markdown 与附件的多文件选择、完整文件夹、ZIP 内容包。文件夹能力不可作为唯一入口，[MDN 的目录选择说明](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/webkitdirectory)也提示旧浏览器兼容差异。手机 Safari 需真实验证，保留 ZIP 和多文件入口。

用户流程：**选择文件 → 自动整理为草稿 → 看缺图/错误和桌面/手机预览 → 保存私密或明确公开发布**。已有规范内容包直接验证；普通 `.md` 不要求手写 YAML，系统生成 ID、slug、时间和附件清单；用户只需核对标题、类型与公开范围。发生日期未知为 null，不能拿上传日伪造经历日期。

管理列表提供标题搜索、类型/标签、草稿/已发布/归档、公开/私密过滤；单篇提供预览、修改元数据、上传新版、历史版本、导出。继续使用外部 Markdown 编辑器，暂不建设站内富文本/代码编辑器。

导入策略：

- 默认 `draft + private`，即便外来 frontmatter 写了 public/published，也须在导入摘要里确认，上传动作不自动公开。
- 导入预检收集全部文章与资源，再解析相对链接。图片优先保持原目录结构，相同文件名在不同文章中互不覆盖；缺附件或歧义列出文件、行、原因和修复建议。
- 远程图片不默认抓取；v1 要求本地附件。避免外部跟踪和服务端请求任意地址，用户可另存后补入；不默认支持 SVG/HTML 作为上传内联内容。
- 新导入缺 ID 时生成并持久化；同 ID 导入进入“更新已有文章”，显示差异并核对 revision/内容哈希，冲突不覆盖。同名、同标题不能自动视为同一篇；相同文件哈希提示重复。
- 单批预检可逐篇标错，但默认整批提交原子完成；支持用户排除错误项后生成新候选批次，不静默半成功。
- 新版本在独立工作区预览，旧公开版本持续可读；发布后 revision 递增，导出标准包应包含系统补齐的 YAML。
- 预览只给已授权主人访问，no-store、不进 sitemap；草稿附件也必须走鉴权 API，不能放到公开静态资源目录。

建议首期限制（待样本验证，不是现有能力）：单 MD 2 MiB、单附件 20 MiB、压缩包 100 MiB、展开总量 250 MiB、最多 100 篇/1000 文件；还应限制路径长度、目录层级、压缩比和处理超时。拒绝路径穿越、符号链接、加密包、嵌套压缩包、扩展名与真实类型不符的文件；持久化原文保留 UTF-8 中文、空格和合法相对路径。[Nest 上传文档](https://docs.nestjs.com/techniques/file-upload)仅提供接收文件的基础能力，这些导入事务和校验仍由应用实现。

## 6. 文件夹与服务职责

立即可用的规范是运行内容根目录下两层结构，不在 public/private 下再套 engineering/recipe/reflection。类型与标签负责分类，文件夹只负责携带一篇正文及附件。项目 docs 永远不自动扫描发布。

```text
仓库/
  docs/                       项目规则、方案、操作说明和内容模板
  content/public/              仅显式授权入 Git 的公开源内容（可选）
  content/private/             现有本地占位，真实私密不在普通 Git
  apps/api/fixtures/demo/      合成 Demo，不复制真实内容
  apps/api/src/modules/content/  权威读取、校验、渲染与权限投影
  packages/content/           现有双端 API/列表/搜索共享适配
  packages/contracts/         数据边界；新增字段由集成者串行处理

外置持久卷 DAYTRACE_CONTENT_ROOT/（建议正式内容库，目录名示意）
  public/<record-id>/index.md
  public/<record-id>/images/...
  public/<record-id>/files/...
  private/<record-id>/index.md
  private/<record-id>/images/...

独立运行时数据根目录/（不放到上述扫描根中）
  imports/<batch-id>/          临时上传与预检；定期清理
  revisions/<record-id>/...    不可变源文件及附件版本
  snapshots/<revision>/...    已校验快照、公开与主人派生索引
  state/                      发布指针、别名保留表、审计与批次元数据
```

上面 `DAYTRACE_CONTENT_ROOT` 表示概念路径；实际环境变量名称以 `packages/config` 为准，实施不得另造并行配置。公开源也可以放外置卷，让上传内容无需 Git/重建网站即可更新。仓库 public 仅作为可选迁移输入，不和运行库同时写同一文章。既有源码目录本轮不搬迁、不新增空壳模块。

后续可在 Nest 下拆 `content-import/`（收取与规范化）、`content-publishing/`（候选快照、版本、回滚），渲染初期留现有 content 模块；仅在 CLI 确实需要复用时再抽 `packages/markdown`，并标 server-only，禁止挂进当前 `packages/content` 默认导出给浏览器打包。

存储首期使用单写者持久文件卷 + 原子替换发布指针，不为少量个人记录先引入 CMS。上传原文是唯一权威来源；HTML、目录、全文索引和图片缩略图可重建。导出 ZIP 含 index.md、附件与校验清单，未来迁移不依赖数据库还原正文。私密源、版本和备份保持相同保护级别；Git ignore 不是备份。未来多副本部署需要共享持久存储与发布协调，不能把单机原子改名假设直接扩展到多实例。

## 7. 文章路由与文档互链

保持现有 [v1 契约](../architecture/contracts/markdown-v1.md)：**稳定 ID 是文章身份，slug 是可改别名，路径层级不绑定分类。**

| 地址 | 规则 |
| --- | --- |
| `/records/<id>/` | 公开唯一规范地址；改标题、类型、文件目录不变 |
| `/records/<slug>/` | 仅公开可见记录解析，308 到 ID；oldSlugs 同样处理 |
| `/h5/records/<id>/` | 现有移动阅读入口；需校验同一 API 规则，公开分享/canonical 统一指桌面规范地址 |
| `/owner/records/<id>/` | 主人详情，保留鉴权；不进入公开 canonical/sitemap |
| `/owner/content/`、`/owner/imports/<batch-id>/` | 建议新增管理与导入结果页，尚未实现 |
| 分类、标签、归档和搜索 | 聚合列表与 query 筛选；不创造新的正文副本地址 |

后续在 Nest 为当前快照建立 `recordById`、`publicAliasToId` 和独立主人索引，增加可见性受控的解析接口（具体 URL 在 API 任务定稿）；Next/H5 不再遍历公开列表来找 slug。先判断权限再返回目标，未知、私密、草稿、归档对访客统一 404，不返回标题或重定向位置。旧别名永久保留为记录归属或墓碑，v1 的 oldSlugs 最多 16 个，超出由运行时别名登记管理，不静默突破现有 schema。保留表查询同样不得泄露私密存在性。

ID 与 slug 命名空间须无歧义，禁止 slug 使用 `rec_` 保留形态。`/records/<id>/` 的 metadata、分享卡、canonical、RSS、sitemap 都从同一公开快照生成；私密切换后统一撤销公开正文、附件、搜索和缓存。不得依赖已缓存的永久重定向授予权限；目标 ID 端点始终重新校验。

[Next permanentRedirect](https://nextjs.org/docs/app/api-reference/functions/permanentRedirect)支持永久跳转；应在响应流输出前解析别名，使常规页面导航有 HTTP 308，而非只靠流中的 meta 跳转。

普通文档互链如 `../另一篇/index.md#小节`：导入期以批次文件映射解析目标 ID，规范化为 `/records/<id>/#<anchor>`；同批未解决目标提示，不猜测。浏览器访问 H5 时可在视图适配链接前缀，持久正文仍保存可迁移来源。公开文章指向私密文章时，公开投影不能包含对方标题/路径等敏感信息，发布前提示作者处理，不能因显示成链接就默认安全。

标题锚点新增语义化且带固定前缀的 ID，重复标题追加序号，统一中文/标点归一化；允许标题重命名改变锚点，不承诺正文小节永久稳定。迁移时保留旧 `section-N` 为当前旧版本兼容别名，并记录映射；后续插入章节不能随意重算既有映射。若需要永久段落定位，应另做持久 block ID 协议，不能声称标题哈希解决了所有变化。

## 8. 发布、回滚与安全边界

建议事务：接收批次 → 私密临时区 → 规范化 → 全量校验/预览 → 核对基线 revision → 生成不可变候选快照 → 原子切换当前指针 → 同步公开/主人索引与缓存。失败保留上一可读版本；进程重启从持久指针恢复，不把当前内存快照当回滚系统。并发更新用 revision/哈希检查，重复发布用批次幂等键。

生产上传端点需要 F1 主人身份、服务端授权、会话与 CSRF 防护、限额及审计；Next 只转发受控请求，Nest 是唯一业务权威。上传文件不进入应用源码或 Next public，避免被构建器执行或静态公开。

回滚是发布旧内容的新修订，仍执行当前可见性策略；例如文章从公开改私密后，回滚正文不自动恢复旧 public。删除公开内容后清理派生物和缓存；隐私撤回不能只换当前页面而保留旧公开版本下载链接。备份要能恢复原文、附件、指针和别名，不只备份 HTML。

## 9. 下一步实施切片与退出条件

以下是建议工作划分，不是本轮已派发的 active 任务，也不改写 F1→F2 主顺序。

1. **渲染兼容性验证**：在受控试验中比较现有 Marked 与 unified，覆盖脚注、表格、代码、中文锚点、附件/站内链接、恶意 URL/HTML；验证 ESM、异步、30KB/200KB/2MiB 长文与限时退出。保留 parseRevision、代码复制结构和灯箱协议，失败可继续使用原解析器。
2. **本地导入服务**：合成三类文章及附件做标准化、错误定位、去重、更新冲突、批次事务和导出；首个纵向切片先单 MD+附件，下一轮补 ZIP/目录与批量互链。
3. **主人管理页**：接入真实身份后的上传、列表过滤、预览与元数据表单；桌面/H5 共用导入服务，手机以文件选择为基线。
4. **发布与持久恢复**：覆盖草稿→公开/私密、更新、撤回、回滚、进程重启、备份恢复。未发布和无权附件不可读。
5. **路由与派生能力**：直接 alias 索引、旧链接、canonical、公开 sitemap/RSS，补 H5 链接适配与隐私缓存清理。

验收至少包括：三类各一篇从原始 MD 到导出恢复；中文空格/重复文件名/缺图/跨文互链；同 ID 更新冲突与重试；公开转私密与旧别名访问负向测试；上传失败后旧版本继续可读；桌面与 H5 同一快照目录和正文一致。新渲染不能把解析器、Shiki、公式或 Mermaid 引入阅读页必要客户端脚本；用当前测量方法复核 141768 gzip bytes 基线及 81920 bytes 预算，不能只凭服务端架构宣布性能通过。iPhone/Safari 上传、预览和长文需单独真机证据。

## 10. 调研范围与限制

本轮通过 Exa 四个检索方向（渲染生态、安全/扩展、内容框架、备选解析器），请求 18 条候选结果，并补读官方文档；18 是请求结果数，不是独立验证的 18 个来源。Context7 核对 unified 官方示例，源码核对已列关键文件。引用均优先项目官方资料，产品是否适合 Daytrace 是本方案判断。

尚未执行：安装候选依赖、两种解析器跑分、实际上传端点、真实身份、数据迁移、真机或部署。本方案提供实施边界与验收依据，不把调研推断当实测结果。
