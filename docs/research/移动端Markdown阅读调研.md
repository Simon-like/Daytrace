# 移动端 Markdown 阅读调研与一期设计建议

日期：2026-10-29。阶段：官方资料调研与方案建议，尚未实现或进行设备测试。

## 1. 结论

Markdown 适合作为内容源；移动端阅读质量主要取决于生成的 HTML、排版、组件行为、资源加载与设备验证。无需为手机维护另一份 Markdown。

建议采用“可迁移 Markdown + 相对路径附件 + 预先渲染的正文页面 + 少量按需交互”的组合。公开展示适合静态生成；私密内容必须额外设计访问保护，不能直接塞进公开静态产物。

Astro 是值得优先验证的候选，尚未最终选型。此次没有对所有框架做性能横评，也没有把候选能力视为实际项目已达到的效果。

## 2. 内容格式与迁移

- 正文约定 CommonMark 基础语法，加 GFM 表格、任务列表、删除线等明确支持的扩展。
- YAML frontmatter 用于标题、稳定 ID、日期、类型、标签与可见性；这是额外约定，不是 CommonMark/GFM 正文规范。最终字段在内容模型阶段确定。
- 每条记录采用独立文件夹，内含主 Markdown 和相对路径附件，文件夹整体移动后仍可阅读。
- 公共内容源也应放在私有仓库或受控存储中，由发布流程选择输出；私密元数据本身不是访问控制。
- 不要求 MDX、框架组件或私有块语法。菜谱的材料和工序可以保持普通标题、列表或表格，由站点模板改善外观。
- 不将整个站点的导航、用户设置都硬塞进 Markdown；内容与附件可迁移是目标，生成索引可以重建。
- 站内关系使用稳定 ID 或统一的链接转换规则，避免文章改名、分类变更后链接失效。实现时须校验附件路径和内部链接。
- Mermaid、公式、脚注和 Obsidian 双链不是统一的基础 Markdown 能力；如要支持，需明确扩展、迁移降级方式与渲染成本，一期不默认全部加入。

依据：[GFM 规范](https://github.github.com/gfm/)、[Astro Markdown 文档](https://docs.astro.build/en/guides/markdown-content/)。

## 3. 手机阅读行为建议

以下尺寸和交互是本项目的设计起点，需通过样稿和真机调整，并非规范统一要求。

| 内容 | 一期建议 | 验证重点 |
| --- | --- | --- |
| 中文正文 | 正文约 17–18 CSS px，行高约 1.75–1.9，手机边距约 20px；桌面限制阅读列宽 | 长时间阅读、混排、放大后无裁切 |
| 标题与长链接 | 标题自然换行，长 URL 和行内代码允许合适的断行 | 长英文标识不撑破页面 |
| 围栏代码 | 独立横滑、保留缩进；复制按钮可触摸，可选软换行 | 横滑不带动整页，复制后无行号污染 |
| 表格 | 独立横滑，保留表头和行列关系；提供溢出提示 | 不强制把所有通用表格转换为卡片，不隐藏重要列 |
| 图片 | 正文保留比例，按屏幕加载合适分辨率，预留位置；细节图可放大 | 图片加载不挤走当前段落，截图小字可看清 |
| 长文目录 | 桌面侧栏，手机展开式目录；支持锚点与浏览器后退 | 导航不盖住标题，阅读位置能正确恢复 |
| 嵌套列表与引用 | 控制缩进、边距和装饰，避免逐层吃掉屏幕宽度 | 多级列表、长引用在窄屏仍可读 |
| 菜谱 | 材料、工序和注意点有清晰标题；工序优先顺序列表 | 烹饪时能快速定位，不必反复找段落 |
| 随想 | 短内容仍能独立展示，补充认识标记日期 | 原话与后续变化均能辨认 |

W3C 的 Reflow 要求普通内容在 320 CSS px 等效宽度下能够重排，数据表格等确实依赖二维布局的内容有例外。这支持“正文不横滑、宽表格局部横滑”的处理；并不意味着所有代码都可无条件豁免重排，需要结合代码含义和可替代呈现验证。

依据：[W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow)。

## 4. 渲染与加载方案

### 候选：构建时处理 Markdown

Astro 原生支持 Markdown、frontmatter 和 GFM，内容集合适合管理具有共同结构的记录。默认 Shiki 代码高亮在生成阶段完成，不需要为了高亮把完整解析器送到手机端。

这适合本项目一期以阅读为主、站外修改内容的边界。但本地 Markdown 的更新需要重新生成和部署，不能宣称实时同步。

图片可在生成阶段处理为多尺寸资源，浏览器使用 `srcset`/`sizes` 选择合适资源。Astro 的 Markdown 图片支持处理；直接放在 `public/` 的资源则按原样复制，不会自动优化。具体 responsive 配置和边界需在实现时验证。

依据：[Astro Markdown](https://docs.astro.build/en/guides/markdown-content/)、[内容集合](https://docs.astro.build/en/guides/content-collections/)、[代码高亮](https://docs.astro.build/en/guides/syntax-highlighting/)、[图片处理](https://docs.astro.build/en/guides/images/)、[MDN 响应式图片](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images)。

### 一期的性能取舍

- 正文直接包含在页面里，避免先显示空壳，再下载解析器和 Markdown 后才出现内容。
- 目录、代码复制、图片放大、搜索只加载各自必要的交互代码；正文阅读不依赖它们全部完成。
- 为图片预留宽高或比例，首屏关键图不盲目懒加载，后续图延迟加载。
- 正文优先本机可用的中文字体，不让完整中文装饰字体阻塞阅读；有特色的字体可克制地用于标题。
- 一期不依赖平滑滚动接管、满屏滤镜、逐段滚动入场或持续背景动画体现流畅。

依据：[MDN 图片元素](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img)、[延迟加载](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Lazy_loading)。

## 5. iPhone 浏览器要求

- 正确设置 viewport，保留浏览器缩放能力。
- 全屏布局或固定导航需要处理安全区；不能让底部入口被系统手势区遮挡。
- 在地址栏展开、收起、横竖屏切换和返回页面时，验证布局及阅读位置。
- 交互不能依赖 hover；目录、图片放大与弹层都要有清楚的关闭方式，并在关闭后恢复阅读。
- 尊重 `prefers-reduced-motion`，减少非必要运动。
- 核心正文先按普通网站交付；添加到主屏幕、离线缓存和后台更新不作为一期默认要求。普通网页阅读无需以开发原生 App 为前提。

依据：[MDN viewport](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)、[WebKit 安全区说明](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)、[MDN 减少动态效果](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)。WebKit 文献用于解释安全区机制，不用它推定所有当前 iOS 版本的具体行为。

## 6. 公开和私密的约束

公开内容可预先生成。私密正文、附件、索引和摘要必须由受保护的入口提供，或生成到完全受保护的个人站点。仅在前端根据登录状态过滤公开下载的数据不成立。

可以在开发方案阶段比较“公开站点 + 整体受保护的个人视图”和“同站请求时鉴权”的维护成本。公开/私密能力已确认，不因展示优先而默认删去手机访问私密记录的可能性。

## 7. 验收矩阵与尚未验证的事项

| 维度 | 建议验收条件 |
| --- | --- |
| 视口 | 至少覆盖 320、375、390、430、768 CSS px 和桌面宽度；断点按内容决定 |
| 设备 | 浏览器自动化与 WebKit 模拟作为预检；真实 iPhone Safari 必须单独验证，不把模拟结果冒充真机结果 |
| 内容 | 中文长文、中英混排、超长标识符、宽表格、长代码、多级列表、连续图片、短感想、缺失图片 |
| 操作 | 目录定位、返回、代码复制、局部横滑、图片放大、搜索、横竖屏、浏览器缩放 |
| 状态 | 冷加载、缓存后访问、较慢网络、图片后到、减少动态效果、未登录和登录 |
| 权限 | 未授权访问正文、附件、搜索索引和公开生成数据均不泄露私密内容 |

建议以 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1 为真实使用的目标，按移动与桌面分别观察第 75 百分位。它们是 Google 的 Core Web Vitals 良好体验阈值，不是当前项目已达成的成绩。上线前使用指定设备与网络的实验测试；上线后有足够样本才评价真实用户百分位，iPhone 仍以实际阅读操作补充验证。

依据：[Web Vitals 定义与阈值](https://web.dev/articles/vitals)。

尚待确定：用户手机型号和系统版本、私密区保护方案、更新与部署流程、真实内容规模、图表与公式扩展需求。当前尚未测量性能、确认最终依赖版本或完成任何真机测试。

## 8. 视觉设计建议

生活手记的温暖来自真实照片、个人表达、舒适的中文排版和时间痕迹。首轮建议以雾白底、墨灰正文、低饱和植物绿和少量木色构成安静基调，避免用大量仿纸纹理和装饰替代内容。

可形成一个与用户诉求直接相关的视觉特征：“那时的我 / 后来的补充”。它在记录中标记认识的变化，也能成为首页的回看片段。勉励自己的话从真实记录摘选，保留日期和原文入口，不做无来源的随机语录墙。

优先验证手机长文页，再做手机首页和桌面首页。同一篇复杂技术 Markdown 要同时出现在不同设备样稿中，防止只用几行短文展示好看的空壳。
